Trustzen

Social proof, testimonial and conversion widgets as a service, built with Next.js 16, React 19 and Tailwind CSS 4. Open source under the MIT licence. This guide takes you from a fresh clone to a live platform with paying customers.

Quick start: clone the repository and upload its app folder (renamed to trustzen), run npm install and npm run build, start the app, then open your domain in a browser. The web installer does the rest — no files to edit.

Introduction

Trustzen lets you run your own social proof platform, like the well-known paid services. Your customers sign up, add their websites, paste one line of code, and show 10 kinds of widgets on their sites: recent purchases and signups, live visitor counts, conversion counters, reviews, announcement bars, coupons, countdown timers, email collectors, cookie notices and custom HTML popups.

The data behind the widgets is real. It comes from the customer's own forms, from Stripe, WooCommerce, Shopify, Zapier or Make (incoming webhooks), from a CSV import, or is added by hand. Customers also get a hosted testimonial collection page, a moderation queue, an embeddable testimonial wall, a list of collected email leads with CSV export, per-widget analytics and outgoing webhooks.

You earn money with paid plans. Plans limit the number of websites, widgets and monthly widget views, and can remove the “Powered by” branding. Payments are accepted through Stripe (automatic renewal), PayPal, Razorpay or manual bank transfer.

The embed script (w.js) is about 14 KB gzipped, has no dependencies, and draws its widgets inside a Shadow DOM, so it never clashes with the customer's own styles.

Words used in this guide: you or the administrator run the platform. Customers are the people who sign up on your platform. Visitors are the people who browse your customers' websites and see the widgets.

Installation

Pick the guide that matches your hosting. Every method ends with the web installer.

Install Trustzen on its own domain or subdomain, for example https://proof.example.com. This address appears in every customer's install snippet, so choose it carefully: changing it later means every customer must update their snippet.

cPanel / shared hosting (Setup Node.js App)

  1. In cPanel open MySQL® Databases. Create a database and a user, then add the user to the database with All privileges. Write down the database name, username and password.
  2. Create the subdomain (e.g. proof.example.com) in Domains and turn on SSL/TLS Status → Run AutoSSL so it has HTTPS.
  3. Open File Manager and upload trustzen.zip (the repository's app folder renamed to trustzen, zipped) to your home folder, e.g. /home/youruser/trustzen, and extract it. Do not put it inside public_html.
  4. Open Setup Node.js App → Create Application:
    • Node.js version: the newest available (22.x recommended)
    • Application mode: Production
    • Application root: trustzen
    • Application URL: your domain or subdomain
    • Application startup file: server.js
    Click Create.
  5. Click Run NPM Install and wait until it finishes.
  6. Copy the command shown at the top of the page (it looks like source /home/youruser/nodevenv/trustzen/22/bin/activate && cd /home/youruser/trustzen). Open Terminal in cPanel, paste it, then run: 
    npm run build
    The build takes 1–4 minutes. It first prints [widget] public/w.js … gzip (the embed script), then builds the app.
  7. Back in Setup Node.js App, click Restart. Open your domain: you will see the installer.

server.js starts the built Next.js app, which serves everything: pages, the API and the files in public, including /w.js. You don't need to copy anything into public_html.

If the build stops with “JavaScript heap out of memory” your plan limits memory. Build on your own computer instead (npm install && npm run build), then upload the whole folder including the .next folder and public/w.js, and only run “Run NPM Install” + “Restart” on the server.

VPS (Ubuntu) with PM2 and Nginx

  1. Install Node.js 22, Nginx and PM2: 
    curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs nginx
sudo npm install -g pm2
  2. Install MySQL (or use SQLite and skip this step): 
    sudo apt install -y mysql-server
sudo mysql -e "CREATE DATABASE trustzen CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'trustzen'@'localhost' IDENTIFIED BY 'choose-a-strong-password';
GRANT ALL PRIVILEGES ON trustzen.* TO 'trustzen'@'localhost'; FLUSH PRIVILEGES;"
  3. Upload the trustzen folder to /var/www/trustzen, then: 
    cd /var/www/trustzen
npm ci
npm run build
pm2 start ecosystem.config.cjs
pm2 save && pm2 startup
  4. Create /etc/nginx/sites-available/trustzen: 
    server {
    listen 80;
    server_name proof.example.com;
    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
    Enable it and add a free SSL certificate: 
    sudo ln -s /etc/nginx/sites-available/trustzen /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d proof.example.com
  5. Open https://proof.example.com to run the installer.
Keep instances: 1 in ecosystem.config.cjs. Rate limits, the 30-second widget cache and webhook duplicate detection are kept in memory, per process. One Node.js process handles a lot of traffic (see Performance).

Docker

The app folder includes a Dockerfile and a docker-compose.yml with MySQL 8.4:

cd trustzen
docker compose up -d --build

Open http://your-server:3000. In the installer choose MySQL with host db, port 3306, database trustzen, user trustzen, password trustzen (change these and MYSQL_ROOT_PASSWORD in docker-compose.yml first). The storage folder is kept in a Docker volume. Put Nginx, Caddy or Traefik with HTTPS in front of port 3000.

Without Compose:

docker build -t trustzen .
docker run -d -p 3000:3000 -v trustzen-storage:/app/storage trustzen

Vercel (with a cloud MySQL database)

Vercel has no permanent disk, so the web installer and SQLite can't be used there. Instead, Trustzen is configured with environment variables and a cloud MySQL-compatible database such as TiDB Cloud Serverless (free tier), Aiven or PlanetScale.

  1. Create a database. In TiDB Cloud: create a Serverless cluster in the region closest to your visitors, open Connect, generate a password and note the host, port (4000), user and password. In the SQL editor run CREATE DATABASE trustzen;
  2. Fork this repository on GitHub (or push your own copy).
  3. In Vercel click Add New → Project, import the repository and set Root Directory to app (the folder that contains package.json). Keep the default build command (npm run build): it also builds w.js.
  4. Add these Environment Variables: 
    DB_DRIVER=mysql
DB_HOST=gateway01.ap-southeast-1.prod.aws.tidbcloud.com
DB_PORT=4000
DB_USER=xxxxxxxx.root
DB_PASSWORD=your-password
DB_NAME=trustzen
DB_SSL=true
APP_INSTALLED=true
ADMIN_EMAIL=you@example.com
ADMIN_PASSWORD=a-strong-password
ADMIN_NAME=Your Name
SITE_URL=https://proof.example.com
  5. Click Deploy. Tables are created automatically on the first visit and the administrator account is created from ADMIN_EMAIL / ADMIN_PASSWORD.
  6. Add your domain in Settings → Domains, and set the same address in Admin → Settings → General → Site URL.
  7. In Vercel open Settings → Functions and choose the region closest to your database for the best speed.

Vercel is fine for a demo or a small platform, but a VPS or cPanel is recommended for production:

  • Uploaded files are not kept (no permanent disk). Paste image URLs for the logo and favicon instead of uploading. Testimonial photos uploaded on the collection page can't be stored either, so a testimonial sent with a photo fails; customers can still send testimonials without a photo, and add photo URLs by hand in the dashboard.
  • Rate limits, the widget cache and webhook duplicate detection are kept per serverless instance.

Local computer (for testing or customising)

cd trustzen
npm install
npm run dev

Open http://localhost:3000 and choose SQLite in the installer. To try widgets locally, add a website with the domain localhost in the dashboard and paste its snippet into any HTML page served from http://localhost (any port).

Web installer

  1. Requirements – checks the Node.js version and that storage is writable.
  2. Database – choose MySQL/MariaDB (host, port, database, user, password, and Use SSL for cloud databases) or SQLite. Click Test connection, then Continue.
  3. Site & admin – enter your platform name, the full site URL (e.g. https://proof.example.com) and the administrator account. Click Install now.

The installer creates all tables, the three default plans (Free, Pro, Agency), the About, Privacy policy and Terms of service pages and three starter blog posts. It writes storage/config.json and locks itself (storage/installed.lock). Sign in at /login. The admin panel is at /admin, the customer dashboard at /dashboard.

To run the installer again (e.g. to switch databases), delete storage/installed.lock and storage/config.json and restart the app. Existing data in the old database is not deleted.

First steps after installing

The admin dashboard shows a Finish setting up checklist. In short:

  1. Settings → General: check the Site URL (it must be your public https:// address; the install snippet and webhook URLs are built from it), add your logo and contact email.
  2. Settings → Widgets: set the branding text, e.g. “Powered by YourBrand”.
  3. Plans: adjust prices and limits.
  4. Settings → Payments: connect at least one payment gateway.
  5. Settings → Email: configure SMTP (password resets and notifications).
  6. Open /dashboard, add your own website and create a few widgets. Then show them on your marketing pages with Settings → Widgets → Show widgets on this website.

Admin panel

Open /admin while signed in as an administrator. The menu has Dashboard, Users, Plans, Payments, Websites, Pages, Blog, Languages, Messages, Settings and System. Administrators also have a customer dashboard (/dashboard) for their own websites, without any plan limits.

Dashboard

Shows the number of users, active paid plans, revenue this month and widget views over the last 30 days, a chart of daily widget views for the last 14 days, the busiest websites, the newest users, the latest payments and the Finish setting up checklist.

Users

Search and filter users (paid, admins, banned). Open a user to edit the name, email, role (user or admin) and status (active or banned), set a new password, or give a paid plan until a date you choose — useful for bank transfers, gifts or testing. The user page also lists their payments.

Banning a user signs them out, and the widgets on all their websites stop loading. Their data is kept.

What is a “widget view”?

One view is counted each time a widget actually appears on a visitor's screen: a popup slides in, a bar is shown, a modal opens. A widget that never shows (wrong page, wrong device, not triggered, below its minimum count) costs nothing. Rotating widgets (recent activity and reviews) count one view for every item they show, so a popup that shows 5 recent purchases on one page view counts 5 views. Use Items per page view in the display rules to control this.

Views are added up per customer account, across all their websites, per calendar month (UTC). They reset on the 1st of each month. When the limit is reached, the customer's widgets stop showing until the next month or until they upgrade. The testimonial wall and the live preview in the editor do not count as views.

Webhooks and paid plans

Incoming webhooks (Stripe, WooCommerce, Shopify, Zapier, Make) and setting an outgoing webhook URL are available to every customer with an active paid plan. On the free plan, webhook requests are refused with HTTP status 402. There is no separate switch for this per plan; the “Webhooks and integrations” line in the plan features is only text.

Administrators and downgrades

  • Administrators never have limits, and their widgets never show branding.
  • When a paid plan ends, the customer moves back to the free plan. Nothing is deleted. Existing websites keep working, but new websites and widgets can't be added while they are above the limit, and each website shows only its first widgets up to the plan's widget limit. The dashboard shows a notice explaining this.

Payments

Every payment from every gateway, with a filter by status. Bank transfers wait here with the customer's transaction reference: click Approve to activate the plan, or Reject. Paying again while a plan is active adds another month or year to it.

Websites

An overview of every website on the platform with its domain, its owner and its activity. Use it to find your most active customers, check a customer's setup when they ask for help, or spot abuse (for example fake activity, see the honest-use policy). Customers create and manage their websites themselves in their dashboard; the admin dashboard also lists the busiest websites of the last 30 days.

Pages & messages

Create content pages (About, Privacy policy, Terms…) in Markdown. They are published at /p/your-slug and can be linked in the footer. {site_name} and {site_email} are replaced automatically. The default Privacy policy already describes what the widgets store — review it with your own legal details before launch. Messages lists contact-form submissions; reply by email with one click.

Blog

Write articles in Markdown at Admin → Blog. Each post has a title, URL slug (/blog/your-slug), excerpt, cover image (upload or URL), meta description and status. Leave the publish date empty to publish now, or pick a future date (UTC) to schedule the post. Published posts appear at /blog, in the sitemap and, the latest three, on the home page. Three starter articles about social proof and testimonials are included. Switch the whole blog off in Settings → General.

Customer guide

This chapter explains the customer dashboard (/dashboard). You can copy parts of it into your own help pages or blog. Each website has its own menu: Overview, Widgets, Events, Testimonials, Leads, Integrations, Analytics and Settings. The top level shows all websites and the plan usage meters (websites, widgets, widget views this month).

Adding a website

  1. Click Add website. Enter a name (only you see it) and the domain, e.g. shop.com. You can paste a full address; https://, www. and the path are removed.
  2. The widgets work on that domain and all its subdomains (www.shop.com, blog.shop.com). For other domains, such as a staging site, add them under Settings → Extra allowed domains (up to 20).
  3. After saving, the website overview shows the install snippet and the status Waiting for first visit.

Installing the snippet

Every website has one snippet. It looks like this:

<script async src="https://proof.example.com/w.js" data-site="aBcD3fGh2JkL"></script>

Paste it once, just before </head>, on every page. Widgets are then managed only from the dashboard; the snippet never changes. After installing, open the website once. The status changes to Installed within a few seconds of the first visit.

PlatformSteps

WordPressInstall a header and footer plugin such as WPCode (Insert Headers and Footers). Paste the snippet into the Header section and save. Clear any caching plugin.
ShopifyOnline Store → Themes → … next to your theme → Edit code. Open layout/theme.liquid, paste the snippet just before </head> and click Save.

The snippet is domain-locked: the widget API only answers requests from the website's own domain, its subdomains and its extra allowed domains. Copying a snippet to another website does nothing.

Widget types

Click New widget, pick a type and you get sensible defaults. Every widget has three tabs: Content (below), Design and Display rules. The live preview updates as you type. Switch a widget off with the Active toggle without deleting it, or Duplicate it to try a variation.

Message templates support placeholders in curly brackets. Click a placeholder under the field to insert it.

1. Recent activity — real purchases and signups as they happen

A popup that rotates through the latest events, e.g. “Anna from Berlin, Germany purchased Pro plan · 2 hours ago”.

  • Show these events – purchases, signups, reviews, custom events.
  • Message – placeholders {name}, {city}, {country}, {product}, {location} (city and country together). Default: {name} from {location} purchased {product}.
  • Name when unknown – e.g. “Someone”.
  • Customer names – first name only (default), initials only, or full name.
  • Link – clicking the popup opens the event's own link, or this one when set.
  • Only events from the last – hours (default 168 = one week, 0 = no limit).
  • Events to rotate – 1 to 30 of the newest events (default 20).
  • Show when it happened and Shuffle the order.

2. Live visitors — how many people are browsing right now

  • Message – placeholder {count}. Default: “{count} people are viewing this page right now”.
  • Count visitors on – the same page, or the whole website.
  • Show from – the widget stays hidden while fewer people are online (default 2). It appears by itself when more visitors arrive.

Visitors count as online while their browser sent a heartbeat in the last 90 seconds (one small request a minute while the page is open).

3. Conversion counter — signups or sales in the last hours

  • Message – placeholders {count} and {hours}. Default: “{count} people signed up in the last {hours} hours”.
  • Count these events – any of the four event kinds.
  • Time period – in hours (24 = today, 168 = a week; up to 90 days).
  • Minimum to show – hidden while the number is lower (default 3), so small numbers never work against you.

4. Reviews — rotating testimonials with star ratings

  • Reviews from – approved testimonials (from the collection page or added by hand), or review events (e.g. sent by a webhook).
  • Minimum rating – 1 to 5 stars (default 4).
  • Reviews to rotate – 1 to 30 (default 10). Shuffle the order.
  • Shorten long reviews after – 60 to 400 characters (default 160); longer texts end with “…”.

5. Announcement bar — a slim bar for news, offers and launches

  • Badge – a short label before the text, e.g. “New”. Empty for none.
  • Text, Button text and Button link (leave the button text empty to hide the button).

Defaults to a top bar shown as soon as the page loads.

6. Coupon — a discount code visitors copy in one click

  • Headline, Text, Coupon code.
  • Copy button text and After copying (e.g. “Copied!”). Copying the code counts as a conversion.

7. Countdown timer — urgency for sales and limited offers

  • Text – shown before the timer, e.g. “Sale ends in”.
  • Count down to – a fixed date (everyone sees the same deadline, set in your time zone) or per visitor (each visitor gets the same amount of time, e.g. 30 minutes, from their first visit; up to 30 days).
  • Button text and Button link.
  • When the timer reaches zero – hide the widget, or show a message (“The offer has ended.”).

8. Email collector — turn visitors into subscribers and leads

  • Headline and Text.
  • Ask for the name too, with placeholders for both fields.
  • Button text and Thank-you message.
  • Consent note (optional) – e.g. a line about your privacy policy, shown under the form.

New subscribers appear under Leads. A visitor who subscribed doesn't see the form again on that browser. Defaults to appearing after 50% scroll and hiding for a day after it is closed.

9. Cookie notice — a simple, friendly cookie consent bar

  • Text, Accept button text, Policy link text and Policy link.

After the visitor accepts, the notice is not shown again on that browser. This is an information notice with an accept button; it does not block other scripts on the page. Websites that need full consent management (blocking tags before consent) should use a dedicated consent tool.

10. Custom HTML — your own message or markup in a popup

  • Your HTML – text formatting, links, lists, headings and images are allowed. Scripts, styles, forms, frames, event handlers and javascript: links are removed when saving (and again in the browser).

Widgets that share a position wait for each other and appear one after the other, never on top of each other. Corner popups keep clear of visible top and bottom bars. On phones, corner popups are shown at the bottom of the screen. On right-to-left websites, left and right corners are swapped. Visitors can close a widget with its close button or the Escape key.

Events

Events are the real activity that Recent activity, Conversion counter and Reviews (review events) widgets show. Each event has a kind (purchase, signup, review or custom), a name, city, country, product, optional link, image, rating (1–5), message and time. The Events page lists them with a filter by kind. You can hide an event from widgets (it stays in the list) or delete it. The list shows how each name will appear publicly, e.g. Shown as “Anna”.

Events arrive from four sources:

Form capture

Turn on Settings → Form capture → Capture form submissions and choose the event kind to create (e.g. signup). The install snippet then watches the website's own forms (signup, checkout, contact). When a form with a name field is submitted, an event is created with:

  • the first name only, from a field named name, first_name, firstname, fname, full_name or your_name (also inside brackets, e.g. billing[first_name]);
  • optionally the city (city, town), country (country) and product (product, product_name, item, plan).

Email fields, passwords, payment fields and everything else are never read. Forms with a password, search or card field, and search forms, are skipped.

Webhooks

Orders from Stripe, WooCommerce, Shopify, Zapier, Make or your own code. See Incoming webhooks.

Manual

Add event on the Events page, for sales from other channels such as phone or in-store orders. Leave the time empty for “now”.

CSV import

Incoming webhooks Paid plans

Every website has a secret webhook URL, shown under Integrations:

https://proof.example.com/api/hooks/<secret token>

Every POST to this URL creates social proof events. The sender is detected automatically from its headers and data (Stripe, WooCommerce, Shopify or generic JSON). You can also force a format by adding ?preset=stripe, woocommerce, shopify or generic.

Keep the URL private: anyone who has it can add events. Click Regenerate URL if it leaks; the old URL stops working immediately and must be updated in every connected service. Provider signatures (Stripe-Signature, X-WC-Webhook-Signature, X-Shopify-Hmac-Sha256) are not checked — the secret in the URL is the authentication.

Stripe

  1. In Stripe open Developers → Webhooks → Add endpoint.
  2. Paste the webhook URL as the endpoint URL.
  3. Select the event checkout.session.completed and save. (checkout.session.async_payment_succeeded, charge.succeeded and payment_intent.succeeded are also understood. Choose only one of them, or the same sale may appear twice.)

WooCommerce

  1. In WordPress go to WooCommerce → Settings → Advanced → Webhooks → Add webhook.

Verifying the signature

X-Trustzen-Signature is sha256= followed by the hex HMAC-SHA256 of the raw request body, keyed with the website's webhook secret: the last part of its incoming webhook URL (/api/hooks/THIS-PART). Regenerating the webhook URL also changes the signing secret. Always compute the HMAC over the raw bytes, before parsing the JSON.

Node.js (Express):

import crypto from "node:crypto";
import express from "express";

const SECRET = process.env.TRUSTZEN_SECRET; // the token from your webhook URL
const app = express();

app.post("/trustzen", express.raw({ type: "application/json" }), (req, res) => {
  const expected = "sha256=" + crypto.createHmac("sha256", SECRET).update(req.body).digest("hex");
  const given = req.get("X-Trustzen-Signature") || "";
  const valid = given.length === expected.length &&
    crypto.timingSafeEqual(Buffer.from(given), Buffer.from(expected));
  if (!valid) return res.status(401).send("Bad signature");

  const payload = JSON.parse(req.body.toString("utf8"));
  console.log(payload.type, payload.data);
  res.sendStatus(204);
});

app.listen(3000);

PHP:

<?php
$secret = 'YOUR-WEBHOOK-TOKEN';
$raw = file_get_contents('php://input');
$expected = 'sha256=' . hash_hmac('sha256', $raw, $secret);
$given = $_SERVER['HTTP_X_TRUSTZEN_SIGNATURE'] ?? '';

if (!hash_equals($expected, $given)) {
    http_response_code(401);
    exit('Bad signature');
}

$payload = json_decode($raw, true);
// $payload['type'] is "lead", "testimonial" or "event"
http_response_code(204);

Delivery is best effort: one attempt, a 5-second timeout, redirects are not followed, and there are no retries. The URL must be a public http:// or https:// address on port 80, 443, 8080 or 8443; private and local network addresses are refused. Reply with any 2xx status quickly and do slow work afterwards.

Privacy & GDPR

Trustzen was designed to collect as little as possible. This is a summary to help you and your customers write privacy notices; it is not legal advice.

What the widgets store in the visitor's browser

  • A random visitor id (tz_v) in localStorage. It is 16 random characters, contains no personal data, and is used only to count live visitors and widget views. It is not shared between websites.
  • Small flags to remember that a widget was closed, a cookie notice accepted, an email submitted or when a per-visitor countdown started (keys starting with tz_, in localStorage or sessionStorage).
  • No cookies are set by the widgets, and requests to the widget API are sent without cookies. There is no cross-site tracking and no fingerprinting.

What the server stores

  • Events: name, city, country, product. Form capture keeps the first name only. Names are anonymised when shown publicly (first name or initials by default); the full name is visible only to the website owner.
  • Live visitors: the random visitor id and the page path, for a few minutes.
  • Statistics: daily counters per widget. No visitor IP addresses are stored for widgets; IP addresses are used in memory only, for rate limits.
  • Leads: the email address and optional name a visitor typed into an email collector, with the page.
  • Testimonials: what the author typed, and an optional photo. The collection page tells authors that their name, title, photo and text may be shown publicly.

Responsibilities

  • Your customers are responsible for informing their visitors (for example in their privacy policy) and for obtaining any consent their local law requires, such as consent for email marketing. The email collector has an optional consent line for this. You process this data on their behalf; the default Privacy policy page says so.
  • Customers can delete events, leads, testimonials and whole websites at any time. Deleting a website deletes all of its data.

Honest-use policy

Social proof works because it is true. Trustzen shows real events and real testimonials; it has no “fake notification” generator. We recommend adding a rule to your Terms of service that customers may only show genuine activity and reviews, and that fake or misleading social proof leads to account suspension. In many countries fake reviews and fake urgency are illegal (for example under consumer protection rules in the EU, the UK and the US). From the admin panel you can review websites and ban accounts that break this rule; banning stops all their widgets at once.

Performance & limits

  • Embed script: w.js is about 37 KB minified and about 14 KB gzipped, with no dependencies. It loads with async, waits for the page, and never breaks the host page: all errors are caught. The build fails if the gzipped size grows above 20 KB.
  • One request per page view: the script fetches the website's configuration (widgets plus their data) in one request. Tracking is batched and sent every 10 seconds and when the page is hidden, with sendBeacon. Pages with a Live visitors widget send one heartbeat per minute.
  • Server cache: each website's configuration is cached in memory for 30 seconds, and browsers may reuse it for 30 seconds. Changes in the dashboard therefore appear on the website within about 30 seconds.
  • Rendering: widgets live in a single Shadow DOM host with a constructable stylesheet, use CSS transitions and respect “reduce motion”.

Adding a widget type

  1. src/widget/types.ts – add the type name to WIDGET_TYPES, its content fields to ContentByType, and its defaults (content, plus any design/rule overrides) to WIDGET_DEFAULTS. Add it to ROTATING_TYPES if it shows a sequence of items.
  2. src/widget/normalize.ts – add a case that validates and clamps every content field.
  3. Runtime – write a renderer in src/widget/runtime/render.ts that returns the widget's element, and call it from the switch in start() in run.ts. If it needs server data (events, counts), add it to buildWidgetData() in src/lib/embed.ts. Add styles to widget.css.
  4. Editor – add the content fields in src/components/dashboard/widget-editor/content-fields.tsx, the icon, name and group in type-meta.ts and src/components/dashboard/widget-types.tsx, a small drawing in type-mockup.tsx, and sample data in preview-data.ts if it shows events.
  5. Messages – add dash.type.your_type, dash.typeDesc.your_type and any new editor.* labels to src/lib/i18n/messages.ts.
  6. Run npm run typecheck, then npm run build (it rebuilds w.js) and restart.

Updating to a new version

  1. Back up the storage folder and your database.
  2. Replace all files except storage (and your .env file, if you use one) with the new version.
  3. Run npm install and npm run build (this also rebuilds w.js), then restart the app.

Database changes are applied automatically the first time the new version starts. Your settings, users, websites, widgets and statistics are kept. Customers never need to change their snippet: /w.js always serves the newest script.

Troubleshooting

Widgets don't show on a customer's website

Open the website, press F12 and look at the Console and Network tabs (filter by w.js and /api/w/). Then check:

CauseSolution
Domain mismatch – /api/w/…/config returns 403 “This website is not allowed to use these widgets.”The page's domain must be the website's domain, a subdomain of it, or an extra allowed domain. www. is handled automatically. Add staging sites, preview domains and second shops under Settings → Extra allowed domains. Shopify's *.myshopify.com preview address is a different domain too.
/api/w/…/config returns 404The data-site key in the snippet is wrong, or the website was deleted. Copy the snippet again.
The config loads but widgets is emptyNo active widget, the widget's schedule has ended, the owner's account is banned, or the monthly view limit is reached (see the usage meter in the dashboard).
The config has widgets but nothing appearsCheck the display rules: pages, devices, trigger (scroll, exit intent), and After the visitor closes it — once closed, a widget can stay hidden for the session, a day or for ever on that browser. Test in a private window. Live visitors and conversion counters stay hidden below their minimum. Recent activity needs events in the chosen period.
Ad blockers and privacy extensionsSome block scripts from unknown domains or with names like “notification”. Test with the blocker off. Using your own domain for the platform helps; there is nothing customers can do for visitors who block it.
Content-Security-Policy on the customer's site – the console shows “Refused to load the script” or “Refused to connect”The customer must allow your platform domain: 
script-src  … https://proof.example.com;
connect-src … https://proof.example.com;
img-src     … https://proof.example.com https:;
img-src is needed for testimonial photos and product images (from your platform and from the stores' image hosts). A strict style-src without 'unsafe-inline' may affect how the widget container is positioned; add 'unsafe-inline' to style-src if widgets appear behind page content.
Mixed content – the platform runs on http://Browsers block an http:// script on an https:// page. Install an SSL certificate and set the Site URL to https://; customers then copy the snippet again.
Caching or optimisation pluginsClear the cache after adding the snippet. Plugins that combine or delay JavaScript (WP Rocket, Autoptimize, LiteSpeed Cache) can break async scripts: exclude w.js from them.
Changes don't appearThe configuration is cached for 30 seconds. Wait, then reload.

Integrations and email

ProblemSolution
Webhooks return 402The website's owner is on the free plan. Incoming webhooks need an active paid plan. Upgrade (or, as administrator, give the user a plan in Admin → Users).
Webhook returns 200 but no event appearsRead the reason in the response (Stripe → Webhooks → the event → Response; WooCommerce → Webhooks → Logs; Shopify doesn't show responses, test with Zapier or curl). Common causes: an unpaid or pending order, an event type that doesn't create events, or a repeated delivery of the same order.
Webhook returns 404The URL was regenerated. Copy the new URL from Integrations into every connected service.
Product name is missing for StripeAdd product to the Checkout Session or Payment Link metadata.
Outgoing webhook not receivedThe URL must be public (no localhost, private IPs or intranet names), use port 80, 443, 8080 or 8443, and answer within 5 seconds without a redirect (use the final https:// address). Your server must allow outgoing connections. There are no retries. Only new leads, collection-page testimonials and captured or webhook events are sent — not events or testimonials added by hand or imported. To test, use a service such as webhook.site.
Signature doesn't matchCompute the HMAC over the raw body before parsing it, with the token from the current webhook URL, and compare it with the whole header including sha256=.
Emails don't arrive (password reset, lead and testimonial notifications)Configure SMTP, switch on Send emails and use Admin → System → Send test. Check the spam folder and set up SPF/DKIM for the sender domain. Customers can turn notifications off per website (Settings → Notifications).
Testimonial photo upload failsThe storage folder must be writable. On Vercel, uploads are not possible (see Vercel).

Installation and server

ProblemSolution
Blank page or “502 Bad Gateway”The app isn't running. Check that npm run build finished, then restart (cPanel: Restart; VPS: pm2 restart trustzen; logs: pm2 logs trustzen).
/w.js returns 404w.js is created by npm run build. Run it again (look for the [widget] public/w.js line) and restart. If you build on another computer, upload public/w.js together with .next.
Build fails with “[widget] build failed”Dev dependencies (esbuild, Tailwind, TypeScript) are missing. Run npm install (not npm install --omit=dev) before building.
“storage folder is writable” failsGive the app user write access: chmod -R 775 storage (and chown it to the user running Node.js).
Database connection failsCheck host (usually localhost or 127.0.0.1), port 3306, and that the user has all privileges on the database. On cPanel the database and username include your account prefix, e.g. myacc_trustzen.
SQLite option failsSQLite needs Node.js 22.13+. Choose a newer Node.js version in your hosting panel or use MySQL.
Snippets or webhook URLs show the wrong address (e.g. localhost)Set the Site URL in Settings → General to your public https:// address.
Can't sign in after installing on HTTPS behind a proxyMake sure the proxy sends X-Forwarded-Proto and Host headers (see the Nginx example).
Visitors get “Too many requests”Behind Cloudflare + Nginx set TRUSTED_PROXY_HOPS=2, so each visitor has their own limit.
Payments are not activatedFor Stripe, check the webhook URL and signing secret, and look at the webhook delivery log in Stripe. Set the correct Site URL.
I forgot the admin passwordUse “Forgot password” (needs SMTP). Otherwise ask another administrator to set a new password in Admin → Users, or delete storage/installed.lock, restart, and run the installer again with the same database and the same admin email: the installer sets the new password on the existing account and keeps all data.
